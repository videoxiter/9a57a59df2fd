# Правила для агентов в этом проекте

## Язык общения — строго русский

- Весь текст для пользователя (промежуточные сообщения, ответы, отчёты, объяснения) — **только на русском языке**.
- Английский допустим только для технических обозначений: имена файлов и функций, API, SQL, названия сервисов и моделей, код.
- Замечание пользователя: английские фразы в отчётах — дефект. Перед отправкой ответа проверить, что в нём нет английских предложений.

## Что это за проект (кратко)

- Статический сайт «Сайт ОТП» (HTML/CSS/JS без сборки), хостинг GitHub Pages:
  `https://videoxiter.github.io/9a57a59df2fd/1bceb335668c/`.
- Бэкенд — Supabase (см. `supabase/functions/api`, `notify`, `cron`; SQL — `scripts/*.sql`).
- План доработок и статусы — `docs/ПЛАН-ДОРАБОТОК.md`.
- Правки JS/CSS не требуют регенерации страниц; версия `V` в генераторах нужна только для ссылок на ассеты в HTML.

## Проверка перед отправкой ответа

1. Ответ полностью на русском (технические имена — можно).
2. Все выполненные действия названы так, как есть: «сделано», «запушено», «нужно сделать тебе» — без вымысла.

## Версии приложения

- Схема: **мажор.функционал.исправление** (`2.3.3`), меняется по правилам владельца:
  новая возможность → средняя цифра +1, исправление → третья +1; больше 9 → следующая цифра.
- **Если исправляешь ту же самую ошибку повторно — добавляй букву**: `2.3.3a`, затем `2.3.3b`
  и так далее. Новая буква ставится только при повторном заходе в ту же проблему.
- Сравнение версий понимает буквы: `2.3.3a` новее `2.3.3`, `2.3.4` новее обеих;
  откат на старую версию запрещён (`scripts/test_version.py`).

## Обязательный порядок работы (правило владельца)

1. **В начале задачи — прочитать документацию проекта**, чтобы не терять контекст:
   - `AGENTS.md` (этот файл);
   - `docs/ПРАВИЛА-ГРАФИКА.md` — нормы линий, особые дни (31 декабря — три смены);
   - `docs/ЖУРНАЛ-РАБОТ.md` — что уже сделано и почему;
   - `docs/ОПРОС-ГРАФИКА.md`, `docs/АУДИТ-И-ПЛАН.md`, `docs/ПЛАН-ДОРАБОТОК.md` — планы и открытые вопросы.
2. **Всё фиксировать в проекте в `.md`**: любое изменение логики, правил, ограничений —
   сначала (или сразу после) в документ, потом в код. Факты и правила не держать «в голове».
3. **В конце задачи — анализ и проверки**:
   - `selftest` (синтаксис изменённых файлов);
   - `python scripts/check_pages.py` — сгенерированные страницы;
   - `python scripts/check_secrets.py` — нет ли секретов в публикуемых файлах;
   - для приложения: `python app/tray/otp_tray.py --selftest`, `scripts/test_tray_handler.py`,
     `scripts/test_tray_click.py`, `scripts/test_live_timer.py`;
   - явно перечислить, что проверено, а что нет.
4. **Убирать за собой мусор тестов**: временные `__preview.html`, файлы-выгрузки
   (`scripts/_names.txt`, `_order.txt`, `_keys.txt` и подобные), снимки для отладки.
   Тестовые скрипты (`scripts/test_*.py`) остаются — они полезны.
