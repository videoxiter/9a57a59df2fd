# Учёт рабочего времени («Стартовая»)

Страница `team/<слаг>/start/` (первый раздел в навигации сотрудника). Считает, сколько
человек реально отработал за день: «Начало смены → перерывы/обед/отсутствие → Завершить
смену». Это **отдельная система**: она не связана с часами увольнительных и переработок
(`otp_requests`), ничего в них не списывает и не начисляет.

Данные лежат в Supabase в таблице `otp_time_events` (каждая кнопка — событие).

---

## Куда вписать токен нового Яндекс-бота

Репозиторий **публичный**, поэтому токен в код и в `assets/js/data.js` попасть не должен.
Нужны два места:

### 1. Для сайта (уведомления в канал «ДисКо») — Supabase Secrets

Токен читает Edge Function, а не браузер:

1. Открой Supabase → **Edge Functions** → **Secrets** (или Project Settings → Edge Functions).
2. Добавь два секрета:

| Имя | Значение |
|---|---|
| `YANDEX_BOT_TOKEN` | OAuth-токен нового бота (`y0_Ag...`) |
| `DISCO_CHAT_ID` | id канала «ДисКо», например `0/0/4f24b544-697c-4e18-a9c1-b39432ee9bf9` |

Если ставишь через CLI:

```bash
supabase secrets set YANDEX_BOT_TOKEN=y0_Ag... DISCO_CHAT_ID=0/0/...
```

> Бот должен быть **участником** канала «ДисКо», иначе API ответит
> `Bot is not a member of the chat`. `chat_id` виден в веб-версии Мессенджера в ссылке на чат.

### 2. Для локальных скриптов (не для сайта) — `.env` Hermes

Файл `G:\LMStudio\Hermes\data\.env` (там же, где креды Confluence). Допиши строки:

```
YANDEX_BOT_TOKEN=y0_Ag...
DISCO_CHAT_ID=0/0/...
```

Этот файл читают только локальные скрипты. Сайту он недоступен, а в git его быть не должно.

### Один раз создать бота

Бот создаётся в Яндекс 360 для бизнеса, токен выдаётся через OAuth — см. официальную
документацию: <https://yandex.ru/dev/messenger/doc/ru/>. Отправка сообщений:
`POST https://botapi.messenger.yandex.net/bot/v1/messages/sendText/`
с заголовком `Authorization: OAuth <токен>` и телом `{"chat_id": "...", "text": "..."}`.

## Шаг 1. Создать таблицу

Supabase → **SQL Editor** → вставить и выполнить `scripts/supabase_time.sql`.

Создаются:

- `otp_time_events` — события (append-only), RLS: anon может читать и добавлять;
- `otp_time_days` — представление со сводкой по дням (начало, конец, отработанные секунды).

## Шаг 2. Развернуть функцию уведомлений

1. Supabase → **Edge Functions** → **New function** → имя `notify`.
2. Вставить код из `supabase/functions/notify/index.ts` → Deploy.
3. Секреты из раздела выше должны быть уже заданы.

Проверка:

```bash
curl -X POST "https://<project>.supabase.co/functions/v1/notify" \
  -H "apikey: <publishable-ключ>" -H "Authorization: Bearer <publishable-ключ>" \
  -H "Content-Type: application/json" \
  -d '{"kind":"shift_start","fio":"Тест Тест"}'
```

Ответ `{"ok":true,...}` — сообщение ушло в канал. Шаблоны сообщений (эмодзи и текст) —
в начале функции, `TEMPLATES`.

| Событие на странице | `kind` | Что уходит в «ДисКо» |
|---|---|---|
| Начало смены | `shift_start` | 🚀 ФИО — начало смены |
| Тех.перерыв №1 / №2 | `break1` / `break2` | ☕ Тех.перерыв №N — ФИО |
| Обед | `lunch` | 🍽️ Обеденный перерыв — ФИО, приятного аппетита! |
| Временное отсутствие | `absence` | 🚶 Временное отсутствие — ФИО (причина) |
| Возврат после перерыва/отсутствия | `return` | 👊 ФИО — снова в деле! |
| Перерыв дольше 15 минут | `break_over` | ⚠️ Перерыв затянулся! — ФИО |
| Обед дольше 60 минут | `lunch_over` | ⚠️ Обед затянулся! — ФИО |
| Начало смены позже графика на 5+ минут | `late` | ⚠️ Зафиксировано опоздание! — ФИО |
| Завершение смены | `shift_stop` | 🏁 Завершение смены — ФИО |

> Опоздание и «затянувшийся» перерыв проверяет **облачная функция `cron`** (шаг 3 ниже),
> а не браузер. Поэтому уведомления приходят даже при закрытой вкладке и выключенном ПК.

## Шаг 3. Расписание проверок (cron) — опоздания и затянувшиеся перерывы

1. Supabase → **Edge Functions** → **New function** → имя `cron`.
2. Вставить код из `supabase/functions/cron/index.ts` → Deploy.
3. В настройках функции → **Schedules** → добавить расписание `* * * * *` (каждую минуту).

Функция каждую минуту:

- читает график с GitHub Pages (`assets/data/schedule.json`);
- берёт **только действующих сотрудников сайта** — список `team` в том же JSON
  (уволенные и посторонние из выгрузки Confluence в уведомления не попадают);
- если смена по графику началась 5+ минут назад, а «Начало смены» не нажато — отправляет
  «Зафиксировано опоздание!»;
- если перерыв/обед идёт дольше 15/60 минут — отправляет «Перерыв/Обед затянулся!»;
- отправленное записывает в `otp_time_notices`, чтобы не дублировать сообщения.

Два предохранителя, чтобы канал не завалило в первые дни:

| Что | Как работает |
|---|---|
| `LATE_FROM` | дата, с которой вообще сообщаем об опозданиях (по умолчанию `2026-11-13`). Меняется секретом Edge Function с тем же именем |
| «человек пользуется системой» | опоздание шлётся только тем, у кого за последние 14 дней есть хоть одно событие. Кто кнопкой не пользуется — просто не попадает в отчёт, без спама |

### Что от чего зависит

| Компонент | Где живёт | Нужен ли ПК |
|---|---|---|
| Страницы сайта | GitHub Pages | нет |
| График и линии (JSON) | GitHub Pages (`assets/data/schedule.json`) | нет |
| События времени | Supabase (`otp_time_events`) | нет |
| Отчёты | браузер (читает Supabase) | нет |
| Уведомления | Supabase Edge Function `notify` → Яндекс API | нет |
| Опоздания/затянувшиеся перерывы | Supabase Edge Function `cron` по расписанию | нет |

ПК нужен только для **обновления данных** (генерация сайта из `itogi/*.txt`), но не для
работы системы.

## JSON API

Всё отдаётся напрямую из Supabase (PostgREST). Заголовки одинаковые:

```
apikey: <publishable-ключ>
Authorization: Bearer <publishable-ключ>
```

Ключ — тот же, что лежит в `assets/js/data.js` (`hrRules.cloud.key`), он публичный,
доступ ограничен RLS-политиками.

### 1. События за день

```bash
curl "https://<project>.supabase.co/rest/v1/otp_time_events?empSlug=eq.8b36020d00c7&day=eq.2026-11-11&order=at.asc" \
  -H "apikey: <ключ>" -H "Authorization: Bearer <ключ>"
```

```json
[
  {"id":"tmg...","empSlug":"8b36020d00c7","empName":"Юрьев Сергей Олегович",
   "day":"2026-11-11","type":"shift_start","slot":null,"at":"2026-11-11T05:02:11+00:00","reason":null}
]
```

### 2. Сводка по дням (готовая, с отработанными секундами)

```bash
curl "https://<project>.supabase.co/rest/v1/otp_time_days?day=gte.2026-11-01&day=lte.2026-11-30&order=day.desc" \
  -H "apikey: <ключ>" -H "Authorization: Bearer <ключ>"
```

```json
[{"empSlug":"8b36020d00c7","empName":"Юрьев Сергей Олегович","day":"2026-11-11",
  "started":"2026-11-11T05:02:11+00:00","stopped":"2026-11-11T13:04:00+00:00",
  "worked_sec":27709,"breaks":2,"absences":1}]
```

Фильтры PostgREST: `eq`, `gte`, `lte`, `in`, `not.is.null`, сортировка `order=`, лимит
`limit=`, offset `offset=`. Пример «все сотрудники за период»:

```
/rest/v1/otp_time_days?day=gte.2026-11-01&day=lte.2026-11-30&select=*&order=day.asc
```

### 3. Линия сотрудника и график на день

График и линии публикуются отдельным JSON (обновляется вместе с сайтом):

```
GET /9a57a59df2fd/assets/data/schedule.json
```

Структура:

```json
{
  "generated": "Окт 2026",
  "schedule": {
    "legend": {"1": {"kind": "shift", "title": "Смена 1", "time": "05:00–13:00",
                     "breaks": ["09:15–09:30","11:30–11:45"], "lunch": null}},
    "months": {
      "2026-11": {
        "shifts": {"Юрьев Сергей Олегович": {"11": {"sym":"1","kind":"shift","title":"Смена 1","time":"05:00–13:00","breaks":["..."],"lunch":null}}},
        "lines":  {"L1.1": {"title":"первая линия","labels":["09.11-13.11"],"weeks":[["Завьялов Максим Вячеславович"]]}},
        "vacations": {}
      }
    }
  }
}
```

- **график на день** — `schedule.months["ГГГГ-ММ"].shifts[ФИО][число]`;
- **линия** — найти свою фамилию в `schedule.months["ГГГГ-ММ"].lines[Lx].weeks[i]` и
  проверить, что дата входит в `labels[i]` (`ДД.ММ-ДД.ММ`).

### 4. Текущий статус

Статус не хранится — он выводится из событий дня (это же делает страница):

| Условие | Статус |
|---|---|
| нет `shift_start` | Ожидание начала смены |
| есть `shift_stop` | Смена завершена |
| последнее событие `break_start` (slot `tech1`/`tech2`) | Технологический перерыв №1/№2 |
| последнее событие `break_start` (slot `lunch`) | Обед |
| последнее событие `absence_start` | Временное отсутствие · причина |
| иначе | Работа |

У каждого события есть `at` (время) и `created` — то есть видно, **когда** какой статус
был получен. Если нужен готовый «текущий статус» одним запросом, можно добавить RPC/SQL-
функцию — скажи, сделаю.

### Типы событий

| `type` | `slot` | Смысл |
|---|---|---|
| `shift_start` | — | Начало смены |
| `shift_stop` | — | Завершение смены |
| `break_start` | `tech1` / `tech2` / `lunch` | Пауза |
| `break_end` | то же | Возврат к работе |
| `absence_start` | `absence` | Временное отсутствие (`reason` — причина) |
| `absence_end` | `absence` | Возврат |

## Что видит руководитель

На странице `start` у руководителя и главного специалиста (`canManage`) ниже кнопок есть
**отчёт по рабочему времени**: период «с/по», сотрудник, таблица «дата · начало · конец ·
отработано · недоработка до 8 ч · перерывы» и итоги. Данные берутся из тех же событий.
